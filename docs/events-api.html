Integration contract · fbgroups tracking

go.b-tarikak Events

How the b-tarikak API reports what happens after a visitor arrives from a Facebook group, so each group can be measured by the customers it brings rather than the clicks it produces.

Endpoint POST https://go.b-tarikak.de/events Auth X-Events-Token Version 2026-08-23

Why this exists

413 Facebook groups each carry a distinct tracking code. A link posted in a group looks like https://go.b-tarikak.de/r/FB-SYR-BER-001; the tracking service counts the click and redirects to https://b-tarikak.de/?ref=FB-SYR-BER-001.

That is where our visibility ends. The service never sees a signup, a verified profile, or a completed delivery — those happen inside your application. Without the events below, the funnel reads 12 clicks → 0 registrations, and a group that sends 200 idle visitors is indistinguishable from one that sends 20 who stay.

The request

POST https://go.b-tarikak.de/events
Content-Type: application/json
X-Events-Token: <secret>

{
  "event_type":    "registration",
  "user_ref":      "usr_9f21c4",
  "anon_ref":      "anon-3f9c1a80b26d4e17",
  "tracking_code": "FB-SYR-BER-001",
  "referral_code": "",
  "occurred_at":   "2026-08-18T14:31:07Z"
}
FieldTypeRequiredNotes
event_type enum yes One of the seven stages below. Anything else is rejected with 422.
user_ref string ≤ 128 effectively Your opaque user id. Absent before an account exists — a download by a logged-out visitor is a real event and is attributed through anon_ref. Referrals and rewards need it.
anon_ref string ≤ 128 until there is a user The id the web app gives itself in the browser before anyone signs up. Send it alone on landing_visit, and together with user_ref on registration — that one call is what tells the service the anonymous visitor and the new account are one person. See Attribution.
tracking_code string ≤ 64 first event only The ref value from the landing URL. Send it on the first event you have it for; later events inherit it — see Attribution.
referral_code string ≤ 64 no Only on registration, when the new user was invited by an existing one.
occurred_at ISO-8601 no When it happened on your side. Omitted means now. Send it when replaying a backlog, or the funnel dates will be wrong.
Never send

No names, e-mail addresses, or phone numbers. user_ref must be opaque — an internal id, not something that identifies a person on its own. The data model has no fields for personal data, so such values would be discarded, but they would still have travelled.

The seven stages

The order is the order of the funnel display, not a sequence to be walked. Every stage is counted on its own and none requires another: a registration with no download is a real state, so is a download by someone who never registered, and "10 registrations, 3 downloads" does not mean seven registrations went wrong. The only thing the stages share is the attribution — which Facebook group each one is owed to.

Reported at most once per user, and — except for download — not deduplicated by the service, so a repeated call is counted twice.

01
click Automatic — do not send

Recorded by the redirect service itself when the link is opened.

02
landing_visit Web app → API → here

A visitor loads b-tarikak.de with a ?ref= parameter. This is the only stage that closes the gap between "clicked in Facebook" and "actually arrived" — without it, a broken landing page looks exactly like an uninterested audience.

It is also where the attribution is born: it carries the tracking code and the browser's anon_ref, and every later stage inherits the group through that id. Skip it and the whole rest of the funnel arrives with no group attached.

03
registration Send from the API

The user account is created. This is the stage that carries the most weight: it also issues the user's own referral code and, if referral_code was supplied, records who invited them.

Send anon_ref with it. This is the moment the person changes name — from a browser id to a user id — and this call is the only place both are known at once. Without it the attribution ends here: the download that follows carries only the user id, which the service has never seen next to a tracking code.

04
download Wherever the download is set going

The app download was triggered. Independent of registration in both directions — report it for someone who never signs up, and expect people who sign up and never tap it.

Report it as late as the platform allows. There are three different things one could count, and they are not the same number: a tap on a button, a transfer actually starting, and the app being on a phone. If you serve the file yourself, fire this from the file handler, not the button. If the link goes to a store, the store is the last thing you can observe — say so in the code comment, because the number then means "sent to the store", and nobody reading a report later can tell that from the name alone. The proof that the app really landed is activation, and only the app itself can give it.

Counted once per person. The one stage the service deduplicates besides click: reloading, a second device, a reinstall. Downloads are repeatable by nature, and without the limit one determined thumb would outrank a group that brought four people. A duplicate is answered with 200 {"gezaehlt": false} — it arrived, it did not count.

05
activation Send from the API

The app was opened for the first time — the only evidence that it is really on a device. Send it from the mobile app on first launch. Previously proposed: identity verification passes (btarikak-verify). Pick one and keep it — see the decision below.

06
qualified Send from the API

The user does the thing the platform exists for, for the first time. Proposed: a first trip offered or a first request posted.

07
conversion Send from the API

The loop closes. Proposed: a match is confirmed by both sides and the item is handed over.

Needs a decision

Stages 05–07 are named generically because the tracking service is not specific to this product. Their meaning for b-tarikak is a business choice, not a technical one, and it must be made once and kept: changing it later makes old and new numbers incomparable without any visible sign that they are.

Attribution

Send tracking_code on the first event where you know it — normally landing_visit. On later events you may omit it: when tracking_code is empty, the service reuses the first known attribution of that person. The first one wins; it is the one that brought them in.

"That person" is the part that has to be got right, because a person changes name halfway through: 

go.b-tarikak.de/r/FB-SYR-KLN-002        click     (recorded here)
        ↓ 302
b-tarikak.de/?ref=FB-SYR-KLN-002
        ↓
landing_visit   anon_ref=anon-3f9c…  tracking_code=FB-SYR-KLN-002
        ↓
registration    user_ref=user-8472   anon_ref=anon-3f9c…     ← the join
        ↓
download        user_ref=user-8472                            → FB-SYR-KLN-002
        ↓
activation      user_ref=user-8472                            → FB-SYR-KLN-002

The registration line is the whole mechanism. It is the only call that knows both names, and it is what lets the service answer "which group?" for every later stage. Leave anon_ref off it and the chain breaks exactly there: the download arrives under a user id that has never appeared beside a tracking code, and it is filed with no group.

A stage with no code and no recognisable person is stored unattributed, never guessed onto a group. A wrong number is worse than a missing one — it moves a group up a ranking that decides where the next 300 posts are written.

The response tells you where the event landed: {"gespeichert": "download", "gezaehlt": true, "tracking_code": "FB-SYR-KLN-002"}. An empty tracking_code means it was stored without a group — worth logging, because it is the first sign that the join above is not happening.

Who sends what

The token is a server secret and must never reach a web build: anything the browser can read, a visitor can read — and qualified and conversion move referral status and hand out rewards. So the browser reports to your own API without a secret, and your API relays with one.

StageProduced byReaches this service via
clickthis service—
landing_visit Flutter web app POST /api/v1/tracking/events → btarikak-api → here
registration btarikak-api direct, with the token
download web app, or whatever serves the file POST /api/v1/tracking/events → btarikak-api → here
activation mobile app, first launch btarikak-api → here
qualified, conversion btarikak-api direct, with the token
The relay is narrow on purpose

POST /api/v1/tracking/events accepts landing_visit and download and nothing else, and it never takes a user_ref from the request body — it reads one from the caller's access token if there is a valid one. A public route that accepted registration or qualified would be a rewards faucet.

Referrals

Every registration receives a referral code in the response. Show it to the user; when someone signs up through it, send that value as referral_code on the new user's registration. 

→ POST /events
  {"event_type":"registration","user_ref":"usr_new","referral_code":"REF-8KD2M"}

← 200 OK
  {
    "gespeichert":  "registration",
    "referral_code": "REF-QW7P3",     // this user's own code, to display
    "referral":      "angenommen"      // outcome for the invitation used
  }

A rejected referral does not invalidate the event — the person did register. The referral field always carries a reason, and suspicious cases are set to review rather than blocked: wrongly turning away a real user costs more than a manual check. Self-referral is refused, and one user can be credited to one referrer only.

Responses and failure

StatusMeaningWhat to do
200 Stored. Body contains gespeichert and, after a registration, the referral fields. Mark the event as sent.
401 Missing or wrong X-Events-Token. Nothing was stored. Do not retry. Fix the configuration.
422 Body does not match the schema — usually an unknown event_type. Do not retry. Log the payload.
5xx / timeout Unknown whether it was stored. Retry with backoff, at most a few times. See below.
Call it out of band

Never block a user-facing request on this call. A signup must not fail because a tracking service is slow. Write the event to a local queue and send it from a worker — that also gives you the retry and the replay for free, and occurred_at keeps the timestamps honest when a backlog drains hours later.

Retries duplicate

Only click and download are deduplicated. A retried registration is counted twice and inflates the funnel. Prefer an outbox row marked sent over a blind retry; if you must retry blind, cap it at two attempts.

The token

Stored on the server in /opt/fbgroups/app/.env as EVENTS_TOKEN, readable by root and the fbgroups service user only: 

ssh root@159.195.216.246 "grep '^EVENTS_TOKEN=' /opt/fbgroups/app/.env"

Put it in the API's own secret store — never in the repository. Rotating it means changing both sides; there is no grace period, so change the application first and the server second, or accept a short window of 401s.

Verify the connection

Run this from the API container. It was verified working on 18.08.2026:

curl -i -X POST https://go.b-tarikak.de/events \
  -H "Content-Type: application/json" \
  -H "X-Events-Token: $EVENTS_TOKEN" \
  -d '{"event_type":"landing_visit","anon_ref":"check-1","tracking_code":"FB-SYR-KLN-002"}'

# expected: HTTP/1.1 200 OK
#           {"gespeichert":"landing_visit","gezaehlt":true,"tracking_code":"FB-SYR-KLN-002"}

# And the stage that used to be missing entirely. Note it carries no
# tracking_code: it inherits the one from the visit above.
curl -s -X POST https://go.b-tarikak.de/events   -H "Content-Type: application/json"   -H "X-Events-Token: $EVENTS_TOKEN"   -d '{"event_type":"download","anon_ref":"check-1"}'

# expected: {"gespeichert":"download","gezaehlt":true,"tracking_code":"FB-SYR-KLN-002"}
#           An empty tracking_code here means the attribution did not carry.
Already confirmed

The btarikak-api container reaches this endpoint over the public hostname and receives 200 with the token, 401 without it. No Docker network configuration is required — that is precisely why the endpoint is protected by a token rather than by an IP rule: the container cannot reach the host's 127.0.0.1, and a bridge address changes whenever the compose network is recreated.

Open questions

  1. What are qualified and conversion for b-tarikak? Proposals above; the decision is yours and should be recorded once. activation now has a concrete meaning — first launch of the app — which is worth keeping, because it is the only stage that proves the app actually reached a phone.
  2. Where exactly does download fire? Today the app is not distributed through a store, so nothing observes a real transfer. Whoever adds the download button decides, and writes the decision into the code: the difference between "tapped a button" and "the file started moving" is invisible in a report that only shows a number.
  3. Does the app need to display a user's referral standing? A read endpoint GET /referral/{user_ref} exists but is deliberately not exposed publicly. Say so and it will be opened behind the same token.
  4. Is landing_visit feasible in the Flutter web app? Answered on 23.08.2026: it is implemented, reported through POST /api/v1/tracking/events so that no secret ships inside the web build.

Receiving service: fbgroups, systemd unit on the same VPS, bound to 127.0.0.1:8090 behind nginx. It never contacts facebook.com and stores no IP addresses — click deduplication uses a daily rotating HMAC of address and user agent.

Questions about this contract go to the fbgroups side, not the API team.
